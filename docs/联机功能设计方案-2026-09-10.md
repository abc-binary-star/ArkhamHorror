# 联机功能设计方案

日期：2026-09-10
范围（已与需求方确认）：**局域网直连** · **保持一人一座位** · **只补齐 WithFriends 同桌多人**
不含：Epic 跨桌活动、AI 顶替空座位、公网穿透与 wss 证书

---

## 0. 结论先行

联机**不是要新建的功能，是已存在但有洞的功能**。上游已经实现了 WithFriends 模式、座位表、每局双向 WebSocket、邀请链接、大厅 UI，连中文文案都译好了。真正缺的是三样：服务端鉴权、房主权威、以及人数不足时的解锁手段。

**最高优先级不是安全，是一个约局必然撞上的死锁。**

`Games.hs:222` 建局时：

```haskell
repeatCount = if multiplayerVariant == WithFriends then 1 else playerCount
```

即 WithFriends 建局者只占 1 个座位，游戏停在 `IsPending`；`Arkham/Game.hs:372-375` 把开局硬门控在人数上：

```haskell
state' = if length players + 1 < playerCount
           then IsPending (pendingPlayers <> [pid])
           else IsActive
```

而 `playerCount` 建局后**没有任何修改路径**——无 lens（`Game/Base.hs:97,194` 只有读取用的 `HasField`）、无 `SetPlayerCount` 消息、无 handler 改它。`PUT /games/:id` 和 `/raw`（`Games.hs:243-260`）都只是把 `Answer` 喂给 `updateGame`，不是配置编辑接口。

⇒ **约好 4 人只来 3 人，游戏永久停在 `IsPending`，`runMessages` 拒绝消费队列（`Game.hs:377-383` 注释），存档作废，只能删局重开。**

这是局域网约局最常见的失败模式，必须第一个修。

| Redis 是否必需 | ✅ 不必需，无 Redis 走单进程内存房间 | `Application.hs:134-135` |

⚠️ 两个由"局域网"前提带来的约束，写进方案而不是忽略：

- **纯 HTTP，无 TLS**。`ws://` 而非 `wss://`，浏览器不会拦（页面本身也是 http，无混合内容问题）。但这意味着**令牌在局域网内明文传输**——可接受，前提是这个端口永远不进公网。
- **注册无门控 ⇒ 任何能连到端口的人都能建账号**。局域网内可接受。必须在文档和启动脚本里写死一句：**不要把 3000/3002 端口暴露到公网**（无邮箱验证 + 无速率限制 + trust 认证的 DB 在同机）。这一条应加进 `offline/README.md` 和启动横幅。

## 3. 设计

### P0-1 人数不足解锁：房主降人数并开局

**这是唯一能救回"来不齐"存档的手段，优先级最高。**

新增 `POST /api/v1/arkham/games/#ArkhamGameId/start`，房主专用。

语义（必须两步都做，缺一不可）：

1. 把 `gamePlayerCount` 改写为当前已入座人数（`arkham_players` 该局的行数）；
2. 若改写后 `length players >= playerCount`，把 `gameState` 从 `IsPending xs` 置为 `IsActive`，然后 `runMessages` 排空被 `IsPending` 挡住的队列，并插入 `ArkhamStep` 保证 undo 完整。

**为什么必须改 `playerCount` 而不能只翻 `gameState`**：`getPlayerCount` 被大量剧本卡直接读取来决定线索数、难度阈值、厄运数——例如 `Act/Cards/NightOfTheZealot/TheDevourerBelow/IntoTheDarkness.hs:27-31`（`playerCount > 3` 分支）、`Treachery/Cards/TheDunwichLegacy/BloodOnTheAltar/StrangeSigns.hs:22-23`（3/4 人放 2 个线索）、`Act/Cards/TheDrownedCity/TheDoomOfArkham/BanishHim.hs:54-55`（≤2 人 Cthulhu rage 4，否则 5）。只翻状态会得到一个"3 人打 4 人难度"的错局，且错得悄无声息。

实现要点：

- `Game` 需要新增 `playerCountL` lens（当前只有 `HasField "playerCount"` 读取实例，`Game/Base.hs:194-195`）。
- 事务模式**照抄** `PendingGames.hs:63-109`：`atomicallyWithGame` → `newIORef` → `newQueue currentQueue` → `runGameApp` → `replace gameId game'` → `insert_ ArkhamStep`。不要自己发明一套。
- 排空队列这一步不能省：`Game.hs:377-383` 的注释明确写了 WithFriends 局的 campaign options 是以 `HandleOption` 消息形式停在持久化队列里的，`runMessages` 在 `IsPending` 期间拒绝消费。不排空就会开局后没有任何战役选项（即 #5418 的翻版）。
- 前置校验：仅 `IsPending` 可用；已开局返回 409；非房主返回 403；`length players < 1` 返回 400。
- **只允许降，不允许升**。升人数会让已在场的玩家面对一个突然变难的局。

前端：`MultiplayerLobby.vue` 在 `IsPending` 且房主视角时，把现在那句纯展示的"还需等待 N 名玩家"（`:178-180`）改成带一个「以 N 人开局」按钮的确认区，文案明确写出后果（难度按 N 人计算）。

### P0-2 房主权威落库

P0-1、P0-4 都依赖它，所以要先落。

- 迁移：`arkham_games` 加 `host_user_id bigint NULL`。
- 建局时写入创建者（`Games.hs:221` 构造 `ArkhamGame` 处）。
- **历史存档回填策略：留 NULL，不要猜**。NULL 语义 = "无房主"，此时所有房主专属能力降级为"任何座位持有者可用"（保持现状不回退），并在 UI 上提示可在管理页指定房主。用 `arkham_players` 最早一行去猜会把中途加入的人误判成房主。
- 新增 `POST /games/:id/transfer-host`（房主或 admin 专用）。
- 前端把 `MultiplayerLobby.vue:28-31` 的 localStorage `isHost` 判断整体换成服务端返回的 `hostUserId === myUserId`。**localStorage 那份要删掉，不是并存**——两份真相必然分叉。
- `GetGameJson` 需要带上 `hostUserId`，前端才知道自己是不是房主。

### P0-3 服务端座位鉴权

修 G2。这是把"限制只活在前端"变成真限制。

**改造点：把连接身份传进 `gameStream`。**

现状 `Games.hs:84-88`：

```haskell
getApiV1ArkhamGameR gameId = do
  userId <- getRequestUserId          -- ← 鉴权在这里发生
  wsOptions <- websocketConnectionOptions
  webSocketsOptions wsOptions $ gameStream gameId   -- ← 但 userId 没传进去
```

WS 握手本身是鉴权的（`getRequestUserId` 在升级之前跑），**问题是升级之后 `gameStream` 内部完全不知道你是谁**，于是 `handleData`（`Shared.hs:236-241`）只能无条件采信帧里的 `playerId`。

设计：

1. 引入连接身份类型，在握手前解析好再传入：

   ```haskell
   data StreamIdentity
     = StreamSeat  !PlayerId      -- WithFriends：本连接绑定的座位
     | StreamSolo                 -- Solo：可代任意调查员
     | StreamSpectator            -- 只读
     | StreamAdmin                -- 绕过
   ```

2. `gameStream :: ArkhamGameId -> StreamIdentity -> WebSocketsT Handler ()`，`handleData` 把身份透传给 `updateGame`。
3. `updateGame` 增加身份参数，替换 `Shared.hs:428-433` 的取值逻辑：

   | 身份 | `answerPlayer response` | 结果 |
   | --- | --- | --- |
   | `StreamSolo` / `StreamAdmin` | 任意 | 照旧放行（**保住一人控多角色**） |
   | `StreamSeat pid` | `Nothing` | 用 `pid`，**不再回退到 `activePlayer`** |
   | `StreamSeat pid` | `Just pid` | 放行 |
   | `StreamSeat pid` | `Just other` | `permissionDenied` |
   | `StreamSpectator` | 任意 | `permissionDenied` |

   注意第二行：现在的 `fromMaybe activePlayer` 本身就是错的——客户端省略 `playerId` 时会静默以"当前轮到谁"的身份行动。有了座位身份就该用它。

4. 顺带修掉 `Shared.hs:460-463` 的 `SetActivePlayer` 包裹：它用同一个 `playerId`，身份纠正后回合归属自动正确。

**⚠️ 与 multi-seat-barrier 的硬耦合（见第 4 节）**：不能一刀切"只能答自己的问题"。`JoinAny` 语义（故事朗读，首个响应者替全桌决定）**就是要**任意座位能答同一个问题。所以鉴权规则必须是"读问题的归属与 join policy"，而不是"读 `gameQuestion` 的 key 是否等于我"。

分两步落地以避免撞车：

- **P0-3a（可独立先做）**：只实现上表中 `Nothing → pid`、`Just other → 拒绝`、Solo/Admin/Spectator 分支。这一步不碰 `JoinAny`，因为当前 `JoinAny` 还没实装（barrier 文档 Phase 3）。
- **P0-3b（必须与 barrier Phase 3 同步）**：`JoinAny` 实装时，鉴权改为查 `saPolicy`——`JoinAny` 的 slot 允许任意座位应答，`JoinAll`/`JoinIndependent` 严格限本座位。**不要自己再猜一套问题归属规则**，那正是 barrier 文档要消灭的脆弱启发式。

### P0-4 观战鉴权

修 G3。`Games.hs:107-122` 加 `getRequestUserId`，并给 `gameStream` 传 `StreamSpectator`。

策略选择（**默认关，显式开**）：

- 默认：观战要求"该局座位持有者 **或** admin"。理由是局域网里 gameId 会通过邀请链接在群里流传，无鉴权等于把手牌全公开。
- 新增 `arkham_games.allow_spectators boolean NOT NULL DEFAULT false`，房主可开。开了之后观战要求"已登录"即可。
- 观战者一律 `StreamSpectator`，写操作全部 403（P0-3 已覆盖）。
- 观战视图必须继续看到全部手牌（这是观战的意义），但**前端要显示明确的"观战中"水印**，避免观战者误以为自己在 playing。`Game.vue:135-138` 已有 `spectate` prop，加视觉标识即可。

### P0-5 座位释放与踢人

修 G5。新增：

- `DELETE /games/:id/seat`——自己离座。
- `DELETE /games/:id/seat/#UserId`——房主踢人。

**这里有个好消息**：释放座位比看起来安全。`getApiV1ArkhamGameOpenSeatsR`（`Game/Debug.hs:274-286`）计算空座位的方式是 `gamePlayerOrder` **减去** `arkham_players` 里的 `investigatorId`。所以**只删 `ArkhamPlayer` 行，座位就自动重新显示为空**。而 `claim-seat` 的 `remapInvestigatorUUID`（`Game/Debug.hs:104-122`）是先从 JSON 里 `SELECT` 出该调查员**当前**的 `playerId` 再替换成新 UUID——所以残留的孤儿 UUID 会被下一个认领者自动覆盖。整条链是自愈的，不需要写反向 remap。

**但有一个必须守住的约束**：释放后到重新认领之间，那个调查员的 `playerId` 指向一个不存在的座位行。此时若引擎正好把一个问题 park 在这个孤儿 `playerId` 上，就没人能答 → 死锁。所以：

- **`IsPending` / `IsChooseDecks` 之前**：无条件允许释放（调查员还没有独立状态）。
- **已开局后**：仅当该调查员**当前没有待答问题**（`gameQuestion` 里没有它的 `playerId`）时允许释放。否则返回 409，并提示房主先处理该调查员的问题。
- 已开局后释放 = 新认领者**接手一个活的调查员**（含手牌、伤害、线索）。这正是"顶替掉线玩家"想要的语义，但 UI 必须在认领前明确告知，否则会有人以为自己在开新角色。
- 释放/踢人必须走 `atomicallyWithGame`，与正在进行的操作串行化。现在的 `claim-seat`（`Game/Debug.hs:294-319`）**没有**走游戏锁，也没记 `ArkhamStep`——它是一个裸 `insert` + 一次跨整个 JSON 的 `replace(current_data::text, ...)`。这在有人同时行动时会竞争。**本次一并把 `claim-seat` 挪进游戏锁**，否则释放和认领会互相踩。

### P1-1 大厅实时化

## 4. 与 `docs/multi-seat-barrier.md` 的边界

那份文档在做后端引擎层的"N 人同时决策"屏障重构（Phase 1 in progress），和本方案在多人路径上重叠。划清边界：

**本方案不碰引擎。** 所有改动落在 API / 传输 / 状态存储 / UI 层，不修改 `runMessages`、消息队列、`AskMap` 折叠规则。

**两处必须协同，不能各做各的：**

1. **P0-3b 依赖 barrier 的 `JoinPolicy`。** 鉴权要判断"这个问题是某个座位专属的，还是全桌谁都能答的"，而 `JoinAll`/`JoinAny`/`JoinIndependent` 正是这个判断的权威来源。barrier 文档的核心主张就是把这个隐式分类变成显式声明式状态（`saPolicy`）。**鉴权应该读它，而不是自己再实现一套问题归属启发式**——后者正是 barrier 文档列为"root smell"的东西。
2. **P0-5 的座位释放与 barrier 的 `saSlots` 交互。** 若一个座位在 `JoinAll` 屏障里还欠一个答案时被释放，屏障永远等不到它 ⇒ 死锁。所以释放的"当前无待答问题"检查必须**同时查 `gameQuestion` 和 `gameSimultaneousAsks` 的 `saSlots`**。barrier Phase 1 落地后这项检查才有第二个数据源可查。

**排期建议**：P0-1 / P0-2 / P0-4 / P1 可与 barrier 并行（无重叠）。P0-3a 可并行。P0-3b 与 P0-5 排在 barrier Phase 1、Phase 3 之后。

另：barrier 文档 `Constraints` 里写了"Do **not** run `stack build`; the user builds and reports errors"，本方案沿用同一约定。

## 6. 分期与验收

**Phase 1 — 救存档（P0-1 + P0-2）**
房主列迁移 + `POST /start` + `transfer-host` + 前端删 localStorage host。
验收：建 4 人 WithFriends 局，只 3 人 join，房主点"以 3 人开局"→ 进入剧本，且**线索数/难度阈值按 3 人计算**（拿 `StrangeSigns` 这类 `playerCount == 3 || playerCount == 4` 的卡实测放 2 个线索，拿 `IntoTheDarkness` 实测 `playerCount > 3` 分支不触发）。战役选项已生效（验证 `HandleOption` 队列被排空，不复发 #5418）。非房主调用 403，已开局调用 409。

**Phase 2 — 锁边界（P0-3a + P0-4）**
`StreamIdentity` 贯通 WS 与 REST；观战加鉴权 + `allow_spectators`。
验收：WithFriends 局中 A 玩家伪造 `playerId` 代打 B 的调查员 → 403；A 省略 `playerId` → 以 A 自己的座位行动（不再是"当前轮到谁"）。Solo 局中一人切多个调查员**全部照常可用**（这是回归红线）。未登录访问 `/spectate` → 401；`allow_spectators=false` 时非座位持有者 → 403。

**Phase 3 — 座位流转（P0-5 + `claim-seat` 入锁）**
离座 / 踢人 / 认领并发安全。
验收：玩家 A 离座 → 座位立即显示为空 → 玩家 B 认领 → B 接手 A 那个活调查员的手牌与状态。A 有待答问题时离座 → 409。两人同时认领同一座位 → 恰好一人成功，另一人得到"已被占用"。

**Phase 4 — 实时与在场感（P1-1 + P1-2）**
大厅改 WS 推送 + 在线状态。
验收：一人认领座位，其他人大厅**无轮询**即刷新（抓包确认 3 秒轮询已消失）。一人断网，其余玩家在 30 秒内看到其掉线标识；恢复后标识消失。

**Phase 5 — 跟随 barrier（P0-3b）**
与 `multi-seat-barrier.md` Phase 3 同批：鉴权改读 `saPolicy`。
验收：`JoinAny` 的故事朗读，任意座位应答均被接受且只生效一次；`JoinAll` 的选牌屏障中，A 代答 B 的 `ChooseDeck` → 403。
